# QACore / red_rider — финальная версия

Финальная интеграция интерфейса QACore Диаса и backend red_rider. См. [подробности объединения](docs/INTEGRATION.md).

Полное локальное приложение: интерфейс HTML/CSS/JavaScript, FastAPI, SQLite и подключаемая AI-модель. Приложение импортирует диалоги, оценивает работу оператора, показывает доказательства, сохраняет апелляции и экспортирует JSON для организаторов.

## Быстрый запуск на Windows

1. Распакуйте архив. Откройте папку, в которой лежит `RUN_WINDOWS.cmd`, в VS Code.
2. Дважды нажмите **RUN_WINDOWS.cmd**. При первом запуске установятся Python-зависимости. Python 3.11+ должен быть установлен; скрипт также умеет использовать доступный Python из локального окружения ChatGPT.
3. Откройте адрес из строки **Application** в терминале: обычно **http://127.0.0.1:8000**. Если порт занят старым сервером, скрипт выберет следующий свободный порт. Терминал оставьте открытым.
4. Нажмите **«Демо-примеры»**, чтобы проверить интерфейс без модели. Для реальных данных заполните **«Подключения»**.

Если переносите новую версию поверх старого проекта, сначала сохраните старую папку как резервную копию. Архив не содержит `.env`, базы `data/` и виртуального окружения `.venv/`: ваши настройки и данные не включены в выдаваемую копию. Чтобы избежать конфликта разных версий, рекомендуется сначала запустить новую версию в отдельной папке.

Если порт 8000 занят старым сервером, остановите старый процесс в его терминале сочетанием Ctrl+C. Либо запустите другой порт:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\start.ps1 -Port 8001
```

Вручную из терминала VS Code:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\setup.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\start.ps1
```

Linux/macOS: `bash RUN_LINUX.sh`. API-документация: http://127.0.0.1:8000/docs.

## Что работает

- Импорт исходного JSON-файла или получение набора через API организаторов.
- Список диалогов с поиском и фильтрами, карточка разговора, номера и временные метки реплик.
- Автоматическая оценка выбранного диалога или всего набора; ограниченное число параллельных вызовов и сохранение каждого готового результата.
- RU, KZ, EN; транскрипты чатов и звонков, ссылка на аудио при наличии.
- Восемь исходных критериев, N/A, числовые шкалы, веса и независимый флаг грубой ошибки.
- Обоснования и переход к исходной реплике по нажатию на доказательство.
- Редактор чек-листов: добавление и удаление критерия, формулировка, вес, тип ответа, шкала, N/A. Изменения сохраняются и используются при следующей оценке.
- Апелляция по критерию; подтверждение или изменение оценки с причиной; перерасчёт итога с сохранением первоначальной оценки.
- Строгий экспорт DEV/PROD в формате JSON 1.0, включая явные ошибки обработки.

## Подключение реальной модели

Откройте **«Подключения»** в приложении:

| Поле | Что указать |
|---|---|
| Название команды | Фактическое название для результата |
| Название модели | Точный идентификатор реально используемой модели |
| Режим | `external_api` для внешнего сервиса, `local` для локального сервера модели |
| Базовый URL модели | OpenAI-compatible API, например `https://api.openai.com/v1`; backend добавляет `/chat/completions` |
| API-ключ | Ключ вашего сервиса. Для локального сервера может не требоваться |
| API организаторов | Полная подписанная GET-ссылка из задания |

Можно также заполнить `.env` вручную по `.env.example`. Изменения через интерфейс сохраняются в локальный `.env`; не публикуйте его в Git. Пустое поле секрета при сохранении оставляет предыдущий секрет без изменений. Сохранённые ключи не возвращаются интерфейсу.

Требуется сервер модели с Chat Completions и JSON mode. Фактическая модель попадает в экспорт. При отсутствии настройки система сообщает об этом и не выдаёт выдуманных оценок. Демо-примеры помечены отдельно: их оценки подготовлены заранее без AI, официальный экспорт для них запрещён.

## Данные и правила расчёта

Источник — исходный ответ API:

```json
{
  "isSuccess": true,
  "error": "",
  "data": {
    "dataset_group_id": "DEV",
    "total_records": 65,
    "records": []
  }
}
```

`records` должен содержать все заявленные записи. У каждой записи: `conversation_id`, `channel`, `language`, `transcript` и необязательный `audio_url`. У каждой реплики: `timestamp`, `speaker` (`client`, `operator`, `bot`, `system`), `text`.

Исходные ID, порядок и время реплик сохраняются. Нумерация доказательств — с 1 по **всему** массиву транскрипта. Оценивается только работа оператора; бот и системные события служат контекстом.

Итог считается кодом по правилам чек-листа, а не берётся из текста модели. При N/A вес исключается и остальные применимые веса нормализуются до 100. Шкальные значения учитывают максимальную ступень шкалы и вес; результат округляется до двух знаков. `critical_flag` передаётся отдельно и автоматически не обнуляет балл.

Изменение чек-листа не меняет исторические оценки. Для применения новой версии запустите переоценку. Официальная выгрузка требует исходных восьми критериев, весов и шкал, а также единой модели и версии конфигурации для всего набора. Пользовательские чек-листы доступны для демонстрации и дальнейшей работы в интерфейсе.

## Выгрузка в Git

В интерфейсе выберите набор, выполните оценку и нажмите экспорт. Приложение сохранит файл в соответствующую папку проекта и скачает дополнительную копию через браузер:

| Набор | Обязательный путь | Записей |
|---|---|---:|
| DEV: 60 чатов и 5 звонков | `results/dev/results.json` | 65 |
| Контрольный набор | `results/prod/results.json` | 10 |

Ошибка оценки не удаляет диалог: в выгрузке остаются его ID, `status: "error"`, пустые `criteria`, `score: null` и причина. Необработанные диалоги не могут быть молча пропущены.

Через терминал из корня проекта:

```powershell
.\.venv\Scripts\python.exe -m app.cli fetch --group-id DEV
.\.venv\Scripts\python.exe -m app.cli evaluate --group-id DEV
.\.venv\Scripts\python.exe -m app.cli export --group-id DEV --subset dev
.\.venv\Scripts\python.exe -m app.cli validate --group-id DEV --subset dev --file results/dev/results.json
```

Для контроля замените `CONTROL_GROUP` на **выданный организаторами** идентификатор; не предполагайте, что он равен PROD:

```powershell
.\.venv\Scripts\python.exe -m app.cli run --group-id CONTROL_GROUP --subset prod
```

Повторная обработка только ошибок и ещё не оценённых диалогов: `evaluate --group-id DEV --retry-errors-only`. При замене модели или чек-листа переоцените весь набор, чтобы выгрузка оставалась согласованной.

Оба файла должны быть доступны в репозитории **до стоп-кода**. Одного локального сохранения или commit без push недостаточно. Код не делает push и не создаёт удалённый репозиторий автоматически.

## Проверка

Все тесты выполняются без платных вызовов модели:

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

Сценарий защиты на 5 минут: открыть диалог → показать критерий и доказательство → показать N/A и итог → подать апелляцию и принять решение → изменить критерий и применить новую конфигурацию. Демо позволяет показать просмотр и апелляцию, а реальную автоматическую переоценку выполняйте с настроенной моделью.

## Структура

`app/` — API, импорт, модель, расчёт, SQLite, апелляции и CLI. `frontend/` — готовый интерфейс без сборки и CDN. `tests/` — модульные и интеграционные проверки. `scripts/` — запуск. `results/` — обязательные каталоги сдачи.
